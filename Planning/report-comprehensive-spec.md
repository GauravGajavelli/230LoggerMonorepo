# Summary Report — Comprehensive Specification

> **Before implementing any changes from this document**, familiarize yourself with the current codebase. The feedback application, pipeline, and frontend may have had changes implemented that this spec doesn't account for. Read the existing code, understand what's already built, and identify any conflicts before writing new code. This spec describes the target design — adapt it to what exists rather than overwriting blindly.

## Purpose and Role in the System

The summary report is the **primary engagement surface** of the entire feedback system. It is the first thing a student sees after clicking the email link, and it serves as both a standalone study aid and a launchpad into the interactive feedback site.

The report must work in two modes simultaneously:
1. **10-second scan** — a student who glances at the top section and closes the tab should still walk away knowing which assessments are affected and roughly how much
2. **3–5 minute review** — a student who reads the full page should have a complete study prioritization plan with specific drill links

### Position in the Communication Chain

```
Email says: "3 patterns, relevant to Exam 2. Click here."
                          ↓
Report shows: Which assessments are affected, by how much,
              which specific patterns to practice, and links
              to each drill.
                          ↓
Site provides: Interactive drills, code replay, step-by-step
               debugging walkthroughs.
```

The report is a superset of the email and a subset of the site. Everything the email says, the report expands on. Everything the report references, the site provides in interactive form.

## Conceptual Underpinnings

### Forward-Looking Organization

The original report design organized information by **pattern** (what went wrong). The redesigned report organizes by **assessment** (what's coming up). This is not just a layout change — it changes the fundamental question the report answers.

Old question: "What did I get wrong on BST?"
New question: "What should I focus on before Exam 2?"

The second question is the one students actually have. Nobody opens debugging feedback because they want a retrospective — they open it because they want to do better on the next thing. The assessment-column layout makes the answer to "what next?" the first thing they see.

### Progressive Disclosure Within a Single Page

The report has three visual tiers, each readable independently:

| Tier | What the student sees | Time | What they learn |
|---|---|---|---|
| Assessment cards (top) | Exam 2: ~20%, 2 drills, 9 min / HW5: ~8%, 1 drill, 6 min | 10 sec | Which assessments are affected and roughly how much |
| Drill columns (middle) | Pattern names, weights, times, test IDs, drill links | 3–5 min | Which specific concepts to practice, in what order |
| Footer | Total count, time, site link, privacy | 5 sec | How to go deeper, trust confirmation |

A student can stop at any tier and have received value proportional to their time investment. This is not progressive disclosure through interaction (click to expand) — it's progressive disclosure through **vertical position**. Scroll further = more detail.

### Urgency Through Structure, Not Decoration

The original design used colored dots (red/amber) to signal urgency. These were illegible (no legend) and emotionally charged (red = alarm). The redesign communicates urgency through:

1. **Column position** — leftmost column is the highest-priority assessment (exam before homework, sooner before later)
2. **Sort order within columns** — top drill has the highest assessment weight
3. **Proportion bars** — visual representation of how much of the assessment overlaps with the student's drills

No colors need to be decoded. No legend is required. The structure itself encodes priority.

### Emotional Neutrality

The report is generated by a system, not written by a person. This framing is critical:
- "Your submission was analyzed" — not "we noticed you struggled with"
- "Overlaps with your practice drills" — not "your weak areas"
- "Patterns were identified" — not "mistakes were found"
- "All drills are optional" — not "we recommend you complete these"

The report should feel like a **dashboard** — informative, neutral, inviting exploration but not demanding it. A student who decides not to engage should feel no guilt.

## Report Structure — Detailed Specification

### Entry Point and Framing

The report is served at the student's token URL: `https://feedback.csse.rose-hulman.edu/feedback?token=abc123`

Students arrive via two paths:
- **From email** — they've read "3 patterns, relevant to Exam 2" and clicked the link
- **From landing page** — they entered their email on the homepage, got redirected, have no prior context

Both paths see the same page. The framing sentence at the top ("Your submission was analyzed. Here's what to focus on.") provides context for landing-page arrivals and reads as a natural header for email arrivals.

### Section 1: Header

```
CSSE 230 · Debugging Feedback              ← system label (small, uppercase, muted)
Binary Search Tree                         ← assignment name (large, prominent)
Your submission was analyzed.               ← framing sentence
Here's what to focus on.
```

**Design rules:**
- System label: 11px, uppercase, letter-spaced, muted color. Identifies the system without demanding attention.
- Assignment name: 20px, semibold. This is the largest text on the page. The student should immediately know which assignment this is about.
- Framing sentence: 14px, secondary color. Two short sentences. "Analyzed" is clinical. "What to focus on" is forward-looking.
- Separator: thin horizontal rule below the header. Marks the boundary between identification and content.

**What is NOT in the header:**
- No test pass rate ("6 of 18 tests"). This was in the original design and was identified as potentially discouraging. The pattern count in the assessment cards serves the same bounding function without being a score.
- No "estimated review time" — this lives in the assessment cards and per-drill cards where it's actionable.
- No student name — the report is private by token; there's no need to address anyone.

### Section 2: Assessment Cards

One card per affected assessment. Cards are arranged horizontally (side by side on desktop, stacked on mobile).

```
┌─────────────────────────┐   ┌─────────────────────────┐
│ EXAM 2                  │   │ HW5                     │
│ Friday, April 10        │   │ Friday, April 10        │
│                         │   │                         │
│ ████████░░░░ ~20%       │   │ ███░░░░░░░░░ ~8%        │
│ of exam content         │   │ of HW topics            │
│ overlaps with your      │   │ overlap with your       │
│ practice drills         │   │ practice drills         │
│                         │   │                         │
│ 2 drills · 9 min        │   │ 1 drill · 6 min         │
└─────────────────────────┘   └─────────────────────────┘
```

**Per card:**
- **Assessment name:** Bold, uppercase, slightly colored by assessment type (muted blue for exams, muted green for homework). The color is subtle — it distinguishes types but does not signal urgency.
- **Date:** Right-aligned on the same line as the name. Day of week + Month Day format (`Friday, April 10`). Including the day of week helps students who think in terms of "this Friday" rather than calendar dates.
- **Proportion bar:** A simple horizontal bar showing what fraction of the assessment content overlaps with the student's drill topics. The bar is subdued (muted blue fill on light gray track). Maximum visual width maps to ~50% — this prevents a student with high overlap from seeing a nearly-full bar that looks alarming.
- **Percentage:** Displayed as `~{N}%` next to the bar. The tilde signals this is an estimate. Never show an exact percentage — the underlying data doesn't support that precision.
- **Overlap label:** "of exam content overlaps with your practice drills" — neutral, forward-looking. Uses "practice drills" (preparation framing) not "weak areas" (deficit framing).
- **Summary:** "2 drills · 9 min" — total drills and total time for this assessment's column.

**Ordering rules:**
1. Assessments with earlier dates appear first (left)
2. Among tied dates, exams appear before assignments, assignments before homework
3. Maximum 3 cards. If more than 3 assessments are affected, the least relevant are collapsed into a footer note: "Also relevant to: ET1 (April 20), Exam 3 (May 6)"

**Single-assessment case:** If all patterns map to one assessment, show a single full-width card. The layout should not look broken or empty.

**Zero-assessment case:** If the pipeline couldn't map patterns to upcoming assessments (missing assessment config), skip the cards entirely and show the drill columns with a simple header: "3 debugging patterns were identified in your submission."

### Section 3: Drill Columns

Below the assessment cards, drills are grouped by their primary assessment target.

```
EXAM 2 · Friday, April 10          HW5 · Friday, April 10
─────────────────────────          ─────────────────────────

┌───────────────────────┐          ┌───────────────────────┐
│ Iterator traversal    │          │ Edge case handling    │
│ logic                 │          │ in remove             │
│                       │          │                       │
│ ~12% of exam content  │          │ ~8% of HW topics      │
│ 5 min · Tests 7, 12   │          │ 6 min · Tests 14, 15  │
│                       │          │                       │
│ Open drill →          │          │ Open drill →          │
└───────────────────────┘          └───────────────────────┘

┌───────────────────────┐
│ Recursive size/       │
│ height confusion      │
│                       │
│ ~8% of exam content   │
│ 4 min · Tests 3, 9    │
│ Also relevant to HW5  │
│                       │
│ Open drill →          │
└───────────────────────┘
```

**Column header:**
- Assessment name + date, separated by a thin horizontal rule below. Same muted styling as the card labels. This visually groups the drills under their assessment.

**Per drill card:**
- **Pattern name:** 14px, semibold, serif font. This is the most prominent element in the card. The name should map to concepts students recognize from lecture (e.g., "Iterator traversal logic" not "Pattern cluster #3").
- **Test names:** Listed explicitly below the pattern name. Use the actual JUnit test method names students would recognize from their IDE (e.g., `testPreOrderIterator`, `testInOrderWithModifications`). These ground the feedback in the student's concrete experience — they remember fighting with `testPreOrderIterator`, and seeing it named here validates that the system analyzed *their* work. If a pattern involves many tests, show the top 3–4 and note "and 2 more."
- **Assessment weight:** "~12% of exam content" — same format as the proportion bar labels in the cards above. Reinforces the connection between this drill and the assessment.
- **Time estimate:** Drill time, not reading time. Displayed alongside the test names.
- **Drill link:** "Open drill →" — links to the specific drill on the feedback site, pre-navigated to the relevant section. The arrow suggests forward motion.

**Test recurrence across columns:** A test or pattern that impacts multiple future assessments **appears in each relevant column**, not just the primary one. For example, if `testRemoveNodeWithTwoChildren` is relevant to both Exam 2 (BST deletion questions) and HW5 (AVL tree operations that build on BST remove), it appears as a drill card in both the Exam 2 column and the HW5 column. Each card frames the same test through the lens of that column's assessment — the Exam 2 card emphasizes the exam-relevant concept, the HW5 card emphasizes the homework-relevant application.

This means drill counts and total time in the assessment cards at the top reflect the full set per column, including recurring entries. The footer's total count should deduplicate — "3 unique drills · 15 min total" — so students don't think they have more work than they actually do.

**Sorting within column:**
1. Approximate assessment weight (highest first)
2. Drill time (shorter first, as tiebreaker)

This means the top-left drill on the entire page is always the highest-impact, most time-efficient thing the student can do. A student who clicks one link and leaves has clicked the best possible link.

**Column layout:**
- Two columns side by side on desktop (min-width 240px each)
- Stacked vertically on mobile (columns become sequential sections)
- If only one assessment, single full-width column
- Maximum depth: ~5 drill cards per column before the page feels long. If a student has more than 5 patterns for a single assessment, consider grouping related patterns.

### Section 4: Footer

```
3 drills · 15 min total · All drills are optional

Open full feedback site →

This report was generated from your test run data.
Only you can see this feedback.
Questions? gajavegs@rose-hulman.edu
```

**Elements:**
- **Summary line:** Total drills, total time, "all drills are optional." This is the commitment calibration — the student knows the total ask. "Optional" removes pressure.
- **Site link:** "Open full feedback site →" — goes to the main overview of the feedback app, not to a specific drill. This is for students who want to explore beyond the recommended drills.
- **Privacy statement:** "Only you can see this feedback." Brief, at the bottom, not demanding attention but present for trust.
- **Contact:** For questions about the feedback, not about the course.

The footer displays the unique count so students don't overestimate the total work.

### How This Data is Produced

The pipeline already produces `frontend.json` with debugging episodes and pattern analysis. A new post-processing step generates the report data:

1. **Extract patterns** from `frontend.json` — each pattern has concept tags, associated test IDs, and test method names
2. **Load assessment config** from `data/{assignment}/assessment-config.json` — maps concept tags to upcoming assessments with approximate weights
3. **Map patterns to assessments** — for each pattern, find ALL assessments that cover its concept tags. The pattern appears in every matching assessment's column, framed through that assessment's lens. Calculate the per-assessment weight for each appearance.
4. **Calculate overlap percentages** — per assessment, sum the concept weights of all patterns that map to it (including recurring ones). Cap at 50% for display (even if actual overlap is higher — a student seeing "~60% of exam" might panic).
5. **Sort and structure** — order assessments by date/type priority, order drills within each assessment by weight then time. Track unique drill count separately from per-column counts.
6. **Output report data** as JSON: `data/{assignment}/output/{student_id}/report.json`

This JSON is consumed by the report page on the frontend. The report can be rendered as:
- A **server-rendered HTML page** (the Express server renders the template with the JSON data)
- A **static PDF** generated via Puppeteer or wkhtmltopdf from the rendered HTML
- A **client-rendered React component** (the frontend fetches the JSON and renders it)

Recommendation: **server-rendered HTML** for the initial version. It's the simplest, fastest to build, and works without JavaScript on the client. The mockup JSX provides the layout reference, but the production version should be a server-rendered EJS/Handlebars template.

### Assessment Config — Per Assignment

Each assignment needs a config mapping its concept groups to upcoming assessments:

**File:** `data/{assignment}/assessment-config.json`

```json
{
  "assignment": "Binary Search Tree",
  "short_name": "BST",
  "full_name": "Binary Search Tree",
  "assessments": [
    {
      "id": "exam_2",
      "name": "Exam 2",
      "date": "2026-04-10",
      "date_display": "Friday, April 10",
      "type": "exam",
      "concept_weights": {
        "bst_traversal": 0.12,
        "bst_insert_remove": 0.08,
        "tree_height_size": 0.08,
        "avl_rotations": 0.15,
        "tree_rank": 0.05
      }
    },
    {
      "id": "hw5",
      "name": "HW5",
      "date": "2026-04-10",
      "date_display": "Friday, April 10",
      "type": "homework",
      "concept_weights": {
        "bst_insert_remove": 0.08
      }
    }
  ]
}
```

**This is a manual config.** You write it once per assignment cycle based on:
- The course calendar (when are the assessments?)
- The syllabus (which sessions/concepts does each exam cover?)
- Past exams or instructor guidance (approximate weighting per concept)

The concept keys (`bst_traversal`, `bst_insert_remove`, etc.) must match the concept tags produced by the pipeline's pattern analysis. These are defined in the assignment's `courseContext.concepts` configuration (e.g., `bst.json`).

**Fallback if weights are unknown:** Use equal weights: if an exam covers 5 concept groups and a student's patterns map to 2 of them, show "~2 of 5 exam topics overlap with your practice drills" instead of percentages.

## Integration with the Server

### Serving the Report

The report is served by the Express server as part of the existing token-authenticated flow:

1. Student visits `GET /feedback?token=abc123`
2. Server validates token → gets student_id, assignment
3. Server checks for `data/{assignment}/output/{student_id}/report.json`
4. If report data exists → render the report HTML template with the data
5. If report data doesn't exist but `frontend.json` exists → generate report data on the fly (run the post-processing step), cache it, render
6. If neither exists → show the null-feedback / upload page

The report page is the default view. The full feedback site (interactive drills, code replay) is a deeper layer accessible via the drill links and the "Open full feedback site" footer link.

### Report Generation in the Pipeline

Add a step to `scripts/process-batch.js`:

```
For each student:
  1. Run pipeline → frontend.json (existing)
  2. Run report generator → report.json (new)
     Input: frontend.json + assessment-config.json
     Output: report.json
```

And to the upload/regeneration flow in the server:

```
POST /api/upload:
  1. Save run.tar
  2. Run pipeline → frontend.json
  3. Run report generator → report.json
  4. Queue regeneration email
```

### Static PDF Option

If you want to attach the report as a PDF to the email (in addition to or instead of linking to the web version):

1. Render the report HTML to a headless browser
2. Print to PDF via Puppeteer: `await page.pdf({ path: 'report.pdf', format: 'A4' })`
3. Attach to the email

This is a nice-to-have for later. The web version is the MVP. The PDF option adds value for students who want to print it or read it offline.

## Design Tokens and Typography

The report mockup uses two font families:

- **Source Serif 4** (headings, pattern names) — serif, editorial feel, signals "this is a document" not "this is a web app"
- **Source Sans 3** (metadata, labels, links) — sans-serif, clean, signals "this is data"

The combination creates a visual hierarchy: serif for the things you read (pattern names, framing sentence), sans-serif for the things you scan (dates, percentages, labels).

**Color palette:**
- Text primary: `#2c2c2a` (near-black, for headings and pattern names)
- Text secondary: `#5f5e5a` (dark gray, for metadata and descriptions)
- Text tertiary: `#888780` (medium gray, for footer and low-priority labels)
- Border: `#d3d1c7` (light gray, for card borders and separators)
- Background secondary: `#fafaf8` (off-white, for card fills)
- Accent (exam): `#4a6d8c` (muted blue, for exam labels and links)
- Accent (homework): `#6b7c6b` (muted green, for homework labels)
- Progress bar fill: `#5576a6` (medium blue, for proportion bars)
- Progress bar track: `#e8e7e3` (light gray)

All colors should use CSS variables for dark mode support if/when the feedback site supports it.

## Edge Cases

### Student with zero patterns
Shouldn't happen if the pipeline ran successfully (every student who ran tests should have at least one debugging episode). But if it does: show a simple message: "No debugging patterns were identified in your submission. This usually means your tests were passing consistently. Nice work."

### Student with many patterns (>5)
Group related patterns by concept category. Show the top 3–5 individually, collapse the rest: "2 additional patterns identified — view on the full feedback site."

### All patterns map to one assessment
Show a single full-width assessment card and a single full-width drill column. No empty second column.

### No assessment config exists for this assignment
Skip the assessment cards entirely. Show a simple header: "3 debugging patterns were identified in your submission." Show drill cards without percentage weights — just pattern name, time, test IDs, and drill link. The report is still useful without the assessment mapping; it just lacks the temporal context.

### Student views the report after the assessment has passed
The assessment card dates will be in the past. The report is still useful as a study reference for future assessments. Consider adding a note if the primary assessment is past: "Exam 2 has passed, but these concepts are also relevant to upcoming assignments."
